# Deploying PANS UNILAG

The whole site runs as **one Vercel project**: the React client is served as static files and the
Express API runs as a Vercel function at `/api`, on the same address. The database is MongoDB
Atlas and images are on Cloudinary.

```
 visitor ──▶ Vercel (one project, one address)
              ├── /             static files from client/dist (SPA fallback to index.html)
              └── /api/*        api/index.js → server/dist/vercel.js (Express)  ──▶ MongoDB Atlas
                                                                               ──▶ Cloudinary (signs uploads)
```

Everything is configured in [`vercel.json`](../vercel.json). There is no server to keep running:
Vercel starts the API when requests come in and stops it when it's idle.

## Before you start

- **Use the official PANS account for every service** (Vercel, MongoDB Atlas, Cloudinary, GitHub),
  never a personal one. Add **a second admin** to each and turn on **two-factor sign-in** for both.
- Secrets (database password, `JWT_SECRET`, Cloudinary API secret) go only into the services'
  settings pages and password manager. Never into the repository, chats or screenshots. If one is
  ever shared by mistake, rotate it (make a new one and replace it everywhere).
- Vercel's free **Hobby** plan is for non-commercial projects. Check that the association's use fits
  its terms; the **Pro** plan removes the restriction.

## 1. MongoDB Atlas

1. Sign in to [cloud.mongodb.com](https://cloud.mongodb.com) with the PANS account and create a
   project called `PANS UNILAG`.
2. **Create a cluster:** M0 (free), provider **AWS**, region **Frankfurt (eu-central-1)**. The API
   runs in Vercel's Frankfurt region (`fra1` in `vercel.json`), so they sit next to each other.
3. **Database Access → Add new database user:** username `pans-api`, an autogenerated password
   (copy it into the password manager), role *Read and write to any database*.
4. **Network Access → Add IP address → Allow access from anywhere** (`0.0.0.0/0`). Vercel's servers
   don't have fixed addresses; the long random password is what protects the database.
5. **Connect → Drivers:** copy the connection string and put the database name `pans-unilag` after
   the host, e.g. `mongodb+srv://pans-api:<password>@cluster0.abcde.mongodb.net/pans-unilag?retryWrites=true&w=majority`.
   This is `MONGODB_URI`.

The free cluster has **no automatic backups**: see [Backups](#backups).

## 2. Cloudinary

Sign in to the PANS Cloudinary account. On the dashboard, note the **cloud name**, **API key** and
**API secret**. Uploads from the dashboard are signed by the API, so no upload preset is needed.

## 3. Vercel

1. Sign in to [vercel.com](https://vercel.com) with the PANS account and **Add New → Project**.
   Import the GitHub repository `pans-unilag-website`.
2. Leave **Root Directory** as the repository root and **Framework Preset** as *Other*;
   `vercel.json` sets the install and build commands and the output folder.
3. Under **Settings → General → Node.js Version**, choose **22.x** (as in `.nvmrc`).
4. Under **Settings → Environment Variables**, add these for **Production** (and Preview if you want
   preview deployments to work):

   | Variable | Value | Secret? |
   | --- | --- | --- |
   | `NODE_ENV` | `production` | no |
   | `MONGODB_URI` | the connection string from step 1 | **yes** |
   | `JWT_SECRET` | 48 random bytes: `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"` | **yes** |
   | `CLIENT_ORIGIN` | the site's address, e.g. `https://pans-unilag.vercel.app` (comma-separate several; link previews use the first) | no |
   | `CLOUDINARY_CLOUD_NAME` | from step 2 | no |
   | `CLOUDINARY_API_KEY` | from step 2 | no |
   | `CLOUDINARY_API_SECRET` | from step 2 | **yes** |
   | `VITE_CLOUDINARY_CLOUD_NAME` | the same cloud name (the browser builds image links with it) | no |
   | `VITE_SITE_URL` | optional: leave unset until there's a custom domain | no |

   `VITE_API_URL` stays unset: the site calls `/api` on its own address. Without `VITE_SITE_URL`,
   the build uses Vercel's production address for link previews, `robots.txt` and `sitemap.xml`.

5. **Deploy.** The build runs `npm ci`, compiles the server to `server/dist` and builds the client.
6. Open `https://<project>.vercel.app/api/health`. It should say `"status":"ok","db":"connected"`.
   A `503` with `SERVICE_UNAVAILABLE` means the API couldn't start: open the project's **Logs** for
   the reason (usually a missing variable or the Atlas network access rule).

## 4. Seed the launch content

Run these from your computer, in the repository, with the **production** `MONGODB_URI`. The scripts
prefer a variable set in the terminal over `server/.env`.

```powershell
# PowerShell (Windows)
$env:MONGODB_URI = "mongodb+srv://pans-api:…@…/pans-unilag?retryWrites=true&w=majority"
npm run seed:check -w server     # validates the seed files, writes nothing
npm run seed -w server           # adds everything that's missing; never changes existing items
npm run content:status -w server # lists the placeholders still to fill
```

```bash
# macOS / Linux
MONGODB_URI="mongodb+srv://…" npm run seed -w server
```

**Never run `seed -- --update` or `seed -- --reset` against production once admins have started
editing:** they overwrite the dashboard's changes with the seed files.

## 5. Admins

Create the two dashboard admins (at least two people should always be able to sign in):

```powershell
npm run create-admin -w server -- --email secretary@example.com --name "Full Name" --role admin
```

Each command prints a generated password **once**. Give it to the person privately and ask them to
store it in a password manager. `--reset-password` and `--remove` manage admins later. Then:

```powershell
Remove-Item Env:MONGODB_URI   # forget the production connection string in this terminal
```

## 6. Check the launch

- [ ] `/api/health` shows `ok` and `connected`.
- [ ] The home page, a few menu pages, an event and the gallery load on a phone.
- [ ] `/admin` signs in; editing an announcement shows on the home page after a reload.
- [ ] A photo upload in the dashboard works (Cloudinary variables).
- [ ] The feedback form sends, and the message appears under **Admin → Feedback**.
- [ ] `/robots.txt` and `/sitemap.xml` use the live address.
- [ ] On an Android phone, Chrome offers **Install app**; once installed, open a page, turn on
      airplane mode, and reopen it: it still shows, with the "You're offline" notice.
- [ ] Paste the address into [Facebook's Sharing Debugger](https://developers.facebook.com/tools/debug/):
      it shows the title, motto and badge, as WhatsApp will.
- [ ] Paste an event's address (e.g. `/events/<slug>`) into the same debugger: it shows that event's
      title, dates and venue, not the site-wide card. Then send it to yourself on WhatsApp.

## 7. Custom domain (when it's ready)

1. In Vercel, **Settings → Domains → Add** the domain (e.g. `pansunilag.org`), and add the DNS
   records Vercel shows at the domain registrar. HTTPS is set up automatically.
2. Set `CLIENT_ORIGIN` to `https://pansunilag.org,https://pans-unilag.vercel.app` (the new address
   **first**: event and opportunity link previews use it; drop the second once it's no longer used)
   and `VITE_SITE_URL` to `https://pansunilag.org`.
3. **Redeploy** so link previews and the sitemap use the new address.

## How the API runs on Vercel

- `api/index.js` re-exports `server/dist/vercel.js`. Each instance builds the app and connects to
  MongoDB on its first request, then reuses both while warm. If start-up fails, that request gets a
  JSON `503` and the next request tries again.
- **Rate limits** (sign-in: 10 per 15 minutes; each form: 5 per hour, per IP address) are counted in
  the `ratelimits` collection, so they hold across every instance. MongoDB deletes old counters
  itself. If the database is briefly unreachable, requests are let through rather than blocked.
- Requests are limited to about 4.5 MB, which is fine: photos upload straight from the browser to
  Cloudinary.
- **Link previews:** WhatsApp, Facebook, X, LinkedIn, Telegram and similar crawlers don't run
  JavaScript, so `vercel.json` sends them (by `User-Agent`) to the function for `/events/:slug` and
  `/opportunities/:slug`; it answers with tags for that event or opportunity
  (`server/src/lib/linkPreview.ts`). Everyone else, Google included, gets the normal app. Crawlers
  cache previews for days: after fixing an event's details, click **Scrape again** in the Sharing
  Debugger.
- **Install and offline reading:** the build writes `sw.js` (see README → Install and offline
  reading); `vercel.json` serves it with `Cache-Control: no-cache`, so phones check for a new version
  on every visit. If it ever misbehaves, replace `client/pwa/sw.js` with one that clears itself and
  redeploy; every phone drops it on its next visit:

  ```js
  self.addEventListener('install', () => self.skipWaiting())
  self.addEventListener('activate', async () => {
    for (const key of await caches.keys()) await caches.delete(key)
    await self.registration.unregister()
  })
  ```

- A long-running server still works for other hosts: `npm run build -w server && npm start -w server`.

## Backups

Atlas M0 has no automatic backups. Back up weekly and before big changes, and test that a backup
restores: step-by-step in [backup-restore.md](backup-restore.md) (`mongodump`, a scratch restore
and `npm run backup:verify -w server`).
